## 비트패킹 (7×7 진입 조건)

BP-PPS 논문 Appendix C. 파울리 문자열을 정수 두 개(X 마스크, Z 마스크)로 담고
교환 판정 = popcount, 부호 = 마스크 AND/XOR, 해시 = 정수 둘.

**7×7 의 벽은 런타임이 아니라 메모리입니다.**

> ⛔ **"타겟 생성 비용은 T1 의 6배(약 7시간)" 는 폐기합니다** (2026-09-04).
> 그 추정은 `δ=1e-5` 표에서 나왔는데 프로덕션은 `δ=1e-8` 이고, 실측하니
> **약 250배** 차이가 납니다.

### 프로덕션 `δ` 로 다시 잰 빛원뿔 (2026-09-03 실행, 여기 처음 기록)

`scripts/03h_lightcone_production_delta.py` → `results/lightcone_production_delta.json`.
`δ=1e-8`, `T=0.5`, `dt=0.05`, 4차 Trotter. **관측량 하나**(중앙 사이트)를 전파한 값:

| 격자 | 중앙 항 수 | 직전 대비 | 모서리 항 수 | 소요 |
|:--|--:|--:|--:|--:|
| 3×3 | 58,068 | — | 21,166 | 7.7 s |
| 4×4 | 2,806,148 | ×48.3 | 72,256 | 822 s |
| 5×5 | 14,387,115 | ×5.13 | 81,202 | 6,942 s |
| 6×6 | 14,207,863 | **×0.99 ← 포화** | 81,096 | 9,153 s |
| 7×7 | **미측정** | | | 실행이 6×6 에서 멈춤 |

**좋은 소식:** 포화는 프로덕션 `δ` 에서도 성립합니다 (6×6/5×5 = 0.99).
`δ` 를 조이면 포화 격자 크기가 커질 수 있다는 우려는 **기각**됐습니다 —
`δ=1e-5` 때와 같은 5×5~6×6 에서 포화합니다. 모서리 사이트는 훨씬 이르게,
훨씬 작은 값(8만 대 1,400만, **175배 차이**)에서 포화합니다.

**나쁜 소식 셋:**

1. **절대 규모가 250배입니다.** `δ=1e-5` 의 6×6 이 56,606 항이었는데
   `δ=1e-8` 에서는 14,207,863 항입니다.
2. **관측량 하나에 2.5시간**이고 7×7 은 관측량이 **98개**입니다. 중앙부
   관측량이 비용을 지배하므로 총비용을 다시 추정해야 합니다 — 단순 곱은
   과대추정입니다(모서리가 175배 쌈).
3. **7×7 을 못 쟀습니다.** `sizes=[3,4,5,6,7]` 로 요청했는데 6×6 에서 멈췄고,
   `mem_floor_gb=3.0` 가드가 걸린 것으로 보입니다. **7×7 의 절대 비용은 아직
   측정값이 아닙니다.**

**T2 진입 전에 할 일:** (a) 7×7 을 비트패킹 엔진으로 다시 시도해 실제 항 수와
메모리를 확정, (b) 98개 관측량의 비용 분포(중앙 대 모서리)로 총비용 재추정.

전환 시 결정할 것:

- `n > 64` 처리 (10×10 은 100큐비트 → `uint64` 두 쌍 또는 구조화 dtype).
  **정렬 엔진의 32큐비트 한계를 먼저 푸는 것이 같은 문제입니다.**
- Julia 쪽 표현을 맞출지
- **등가성 검증은 4×4 에서.** 두 엔진의 계수를 항 단위로 비교할 수 있는
  마지막 규모입니다 (TEST 17~22 가 하는 일)

## 2026-09-04 — 문자열 dict 를 마지막 남은 곳에서 걷어냈습니다

훈련은 `f918ac7` 에서 이미 옮겨갔지만 **타겟 생성은 아직 오라클 엔진이었습니다.**
프로젝트에서 가장 비싼 단계가(4×4 관측량 하나 822초, 5×5 하나 2.5시간) 가장
느린 엔진 위에 있었던 셈입니다.

### 1. 패킹 키 단사 — 이제 소리를 냅니다

가드가 **하나도 없었습니다.** 세 곳이 각자 `x | (z << 32)` 를 직접 만들고
있었고(`to_sorted_arrays`, `trainer._packed_keys`, `trainer._sorted_setup`),
어디에도 폭 검사가 없었습니다. 실측한 실패 형태:

```
x = z = 1<<40  ->  키 0x10000000000     # z 가 uint64 밖으로 통째로 밀려남
```

즉 33큐비트 위에서는 **z 가 다른 파울리들이 전부 같은 키**가 되고, 계수가
말없이 합쳐지고, 그 뒤 모든 결과가 틀립니다. 예외도 경고도 없이.

고친 방식: 패킹을 `propagation_sorted.pack_key` 한 곳으로 모으고, 세 층위에서
막습니다 — `assert_key_width(n)`(설정 시점, O(1)), `pack_key(x, z)`(항 하나),
`to_sorted_arrays`(SPO 전체를 벡터화 `max()` 한 번으로). 트레이너와 타겟
생성기가 셋업에서 `assert_key_width` 를 부르므로 **7×7 은 몇 시간 뒤가 아니라
시작하자마자 멈춥니다.** TEST 22 가 고정합니다.

부수적으로 `to_sorted_arrays` 가 빨라졌습니다. 1.2M 항짜리 타겟을 파이썬
`sorted()` 로 튜플 정렬하던 것을 `np.fromiter` + `argsort` 로 바꿨습니다.

### 2. 타겟 생성이 정렬 엔진으로

`TargetGenerator(engine=...)` — `'string'` | `'sorted'` | `'gpu'`.
`generate()` 와 `generate_series()` 둘 다. 설정은 `target.engine`(`ansatz_ibm.yaml`)
과 `time_sweep.engine`(`time_sweep.yaml`), **기본값 `sorted`**.

문자열 오라클과 대조 (`generate()` 전체, 모든 관측량):

| 격자 | 항 수 | support 차이 | 최대 계수편차 | 문자열 | 정렬 | |
|:--|--:|--:|--:|--:|--:|--:|
| 2×2 | 472 | 0 | **0.000e+00** | 0.11 s | 0.31 s | 0.4배 (교차점 아래) |
| 3×3 | 500,154 | 0 | **0.000e+00** | 166.7 s | 19.9 s | **8.4배** |

**항 단위로 같습니다.** 4×4 프로덕션은 관측량당 280만 항이라 3×3 보다 더
위쪽이고, GPU 는 그보다 더 위(120만 항에서 17.3배)입니다.

### 3. GPU 경로의 동기화 병목을 먼저 치웠습니다

`propagate_forward_sorted` 는 `stats` 를 받으면 게이트마다
`float(xp.sum(coeffs**2))` 를 **두 번** 했습니다. cupy 에서 이건 게이트당 두 번의
device→host 동기화라, 14,000 게이트짜리 타겟 청크 하나에 **28,000번** 파이프라인이
비워집니다. 하필 GPU 를 가장 원하는 워크로드에서요. 그런데 타겟 생성은 `stats`
가 필요합니다(`eps_trunc` 가 결과에 실립니다).

고쳤습니다: 누적을 0-d 디바이스 배열로 두고 **끝에서 한 번만** 변환하고, 각
게이트의 출력 노름을 다음 게이트의 입력 노름으로 이어받아 리덕션 수도 절반으로
줄였습니다. **numpy 에서 옛 경로와 비트 단위로 동일**합니다 — 4개 케이스에서
`eps_trunc` 차이가 정확히 `0.000e+00`, 키·계수 배열도 `array_equal`.

### ⚠️ 다만 `eps_trunc` 는 엔진마다 다릅니다 (이전부터)

SPO 는 항 단위로 같지만 **절단 추정치는 같지 않습니다.** 문자열 엔진은 버리는
항을 항별로 누적하고, 배열 엔진은 게이트마다 노름 차분으로 잡습니다:

| | 문자열 | 정렬 |
|:--|--:|--:|
| 2×2, `eps~1e-7` | 3.541e-07 | 6.726e-07 (**2배**) |
| 3×3, `eps~1e-5` | 1.473644e-05 | 1.473457e-05 (4자리 일치) |

원인은 상쇄입니다 — 노름 차분은 `1.0 - 1.0` 에서 `1e-10` 을 뽑는 계산이라,
버려진 총 노름이 작을수록 유효숫자가 남지 않습니다. **`eps_trunc` 가 `1e-6`
아래로 내려가는 영역에서는 배열 엔진의 추정치를 자릿수 이상으로 믿지 마세요.**
적응적 절단(`adaptive_delta`)이 이 값을 쓰므로 관련이 있습니다. 훈련은

### 다음 관문은 키 폭입니다

이제 4×4·5×5 는 전 구간이 배열 엔진 위에 있고, **7×7 을 막는 것은 속도가 아니라
32큐비트 키**입니다. 설계 메모: 지금 `_lookup` 이 `searchsorted` 를 쓰는데,
이것이 128비트 키로 넘어가는 걸 어렵게 만드는 유일한 부분입니다 (구조화
dtype 은 cupy 가 정렬을 지원하지 않습니다). 피할 수 있습니다 —
`union = anti ∪ (anti^flip)` 은 flip 에 대해 닫혀 있고 `union ∩ keys = anti`
이므로, `old_partner = old_self[argsort(union ^ flip)]` 이고 `old_self` 는
union 을 만들 때의 argsort 에서 바로 나옵니다. **그러면 커널이 `sort`/`argsort`
와 동등 비교만 쓰게 되고, 둘 다 안정 정렬 두 번(LSD 기수)으로 2열 키에 그대로
확장됩니다 — numpy 와 cupy 양쪽에서.** 아직 구현하지 않았습니다.
