# 03 — 엔진과 성능

담당 범위: Pauli propagation 엔진의 표현·속도·메모리. **7×7 진입 전에 반드시
처리해야 하는 항목들**이 여기 있습니다.

## 왜 지금 중요한가

4×4 T1-T stage 1의 k=1 스냅샷만으로 이미:

```
n_terms 8,304,835   largest_observable 1,239,943   targets_k1.json 364MB
```

문자열 키 dict 기준 항당 대략 190바이트 → 8.3M 항이 ~1.6GB. **49큐비트에서는
현재 표현으로 못 갑니다.**

## 비트패킹 (7×7부터, 4×4는 그대로)

BP-PPS 논문 Appendix C. 파울리 문자열 `P ∈ {I,X,Y,Z}^n` 을 문자열이 아니라
정수 두 개(X 마스크, Z 마스크)로 담습니다. n=49면 각각 `uint64` 하나, 즉 항 하나가
16바이트 + 계수 8바이트입니다. 문자열 dict 대비 열 배 이상 줄고, 더 중요하게는
**게이트 적용이 비트 연산**이 됩니다:

- 교환 여부 판정 = popcount 한 번
- 부호 = 마스크 AND/XOR
- 해시 = 정수 두 개

현재 `src/bppps/propagation.py` 는 `Dict[str, float]` 입니다. 전환 시 결정할 것:

- n > 64 를 처리할 방법 (10×10은 100큐비트 → `uint64` 두 쌍, 또는 numpy `uint64`
  배열 + 구조화 dtype)
- dict 를 유지할지, 정렬 배열 + 병합으로 갈지. 후자가 캐시 지역성이 훨씬 좋고
  벡터화가 되지만 코드가 커집니다
- Julia 쪽(`julia/src/bppps_engine.jl`)과 표현을 맞출지

**등가성 검증은 4×4에서** 해야 합니다 — 두 엔진이 같은 입력에 같은 계수를
내는지 비교할 수 있는 마지막 규모입니다.

## 타겟 캐시 형식

지금은 JSON입니다. 364MB/스냅샷이고 파싱이 느립니다. 비트패킹으로 가면 자연스럽게
`npz` 또는 `hdf5` (마스크 배열 + 계수 배열) 로 갑니다. 이건 비트패킹과 같은
작업으로 묶는 게 맞습니다.

## Julia 엔진

- `PauliPropagation.jl` 은 **선택적 의존성**입니다. `julia/Project.toml` 의
  `[deps]` 에서 뺐고, `HAS_PAULI_PROPAGATION` 가드로 감쌌습니다. 실제 훈련은
  `julia/src/bppps_engine.jl` 의 자체 구현이 합니다.
- `julia/scripts/check_env.jl` 가 엔진, 모델 계약, PauliPropagation API 를
  검증합니다. 데스크탑에서 Julia를 처음 쓸 때 이걸 먼저 돌리세요.
- **Julia는 커플링을 재생성하지 않습니다.** `model_config.json` 을 읽고 본드
  순서를 검증만 합니다. 예전에 Python은 `for x, y`, Julia는 `for y, x` 로 수직
  본드를 열거해 두 파이프라인이 다른 모델을 풀고 있었습니다.

  결론이 바뀌었으니 그쪽을 보세요.
- 적응적 절단(adaptive truncation)이 시간 스윕에서 실제로 도움이 되는지.
  T1-T stage 4의 δ 스윕이 근거를 줍니다.
- ~~**병렬화·GPU 는 아직 손도 대지 않았습니다.**~~ **닫혔습니다 — 아래
  "2026-09-03 GPU 재판정" 절이 최종입니다.** 이 항목이 세운 순서(①비트패킹 →
  ②스레드 → ③GPU)는 절반만 맞았습니다. 비트패킹과 정렬병합은 그대로 이득이
  맞지만, 그 뒤에 GPU 가 온다는 부분이 틀렸습니다 — 이 커널은 정렬병합으로
  바꾼 *뒤에도* GPU 대상이 아닙니다. 게이트가 순차 체인이고 게이트당 배열
  호출이 35개라 오버헤드가 산술을 압도합니다. 아래 남기는 것은 기록용입니다.

  **병렬화·GPU 는 아직 손도 대지 않았습니다.** Python `propagation.py` 도 Julia
  `bppps_engine.jl` 도 단일 스레드 `Dict{String,Float64}` 입니다. 데스크탑
  Ryzen 5 5600 은 6코어/12스레드인데 항상 1코어만 씁니다. 순서는
  ① 비트패킹(`UInt64` 키) → ② 스레드 병렬 → ③ GPU 입니다. GPU를 먼저 보면 안
  되는 이유는, 지금 커널이 문자열 해시맵 삽입이라 GPU로 옮길 대상 자체가
  아니기 때문입니다. 정렬 기반 병합으로 바꾼 뒤에야 GPU가 의미를 가집니다.
  (01 세션에서 나온 질문. 자세한 근거는 `01-scale-plan.md` 의 "왜 CPU만 쓰나".)

## 2026-08-30 자율 세션 — 목표와 순서

사용자가 잠들기 전 승인한 범위. 순서대로 진행하고 각 단계를 커밋합니다.
메모리는 **실시간 감시**. `.wslconfig` 로 WSL 캡을 11GB → 19GB(가용 17GB)로
올림 (사용자가 직접, `wsl --shutdown` 후 세션 재개). 17GB 기준으로 진행.

1. **statevector pilot** (`scripts/03_statevector_pilot.py`, 신규) — 손으로 짠
   RX/RZZ statevector applier로 (a) 목표1/T1-T: T={0.5,1,2,4} × layers
   [2,3,4,6,8] 직접 훈련 하한, (b) 목표3: 바닥상태 ceiling-vs-layers
   (L=1..8). 타겟 캐시·절단 불필요, 둘 다 ED 대조. 예상 ~1시간.
2. **T1-T stage 1 병렬화** — 기존 `propagation.py`/`target_generator.py` 는
   건드리지 않고 (검증된 오라클), 새 오케스트레이션 스크립트가 32개 관측량을
   `multiprocessing.Pool` 로 나눠 각자 파일로 저장. 메인 프로세스가
   `/proc/meminfo` 를 몇 초 간격으로 감시하다 위험 수위에서 `pool.terminate()`.
   k=2, 4, (되면) 8 재시도.
3. **비트패킹 엔진** (신규 모듈, 기존 문자열 엔진은 그대로 — `CLAUDE.md` 하드룰
   4, 4×4 프로덕션 경로는 안 바꿈) + 4×4 등가성 회귀 테스트.
4. **정렬 병합 + 코어 병렬** — `numba` (`@njit(parallel=True)`, `prange`) 로
   비트패킹 표현 위에서. 문자열 dict 엔진과 벤치마크 비교.
5. **GPU 평가** — 4번이 실제로 통과한 뒤에만. `cupy` (RTX 2060, CUDA 13.1
   드라이버, `nvcc` 없음 → `cupy-cuda12x` 프리빌트 휠 사용). CPU 스레드 버전과
   같은 작업으로 벤치마크해서 **실제로 더 빠를 때만** 채택. 6GB VRAM 한계 기록.

각 단계는 그 자체로 커밋 가능한 결과물을 남기고, 실패해도 이전 단계 결과는
살아있게 설계합니다.

## 병렬화의 결론 (2026-08-30) — 스케일 문제는 병렬화로 안 풀립니다

§2(stage 1 병렬화)를 실제로 돌린 결과를 남깁니다. `02b_time_sweep_parallel.py`
(6워커 `multiprocessing` + numba 엔진 + 실시간 메모리 감시)로 4×4 T1-T stage 1
을 재시도했고, **15시간 동안 32개 관측량 중 6개만** 끝났습니다 (k=1 6개,
k=2 는 X_0 하나). 사용자 결정으로 취소.

원인은 병렬화 효율이 아니라 **항 수 폭발**입니다:

```
X_0    : k=1     31,640항  →  k=2  3,820,095항   (120배, 4.2시간)
X_6/X_10: k=1 약 1,230,000항  →  k=2 미도달
```

워커는 전부 96~98% CPU 로 정상 작동했고 메모리도 여유가 있었습니다(하한
3GB, 실제 9~11GB 유지). 즉 **엔진도 병렬화도 제 역할을 했는데 문제 규모가
그걸 압도**합니다. 코어를 32개 써서 관측량을 하나씩 맡겨도 관측량 하나가
며칠이므로, `k=4`(T=2.0) 는 현재 표현으로 도달 불가입니다.

**교훈**: `k`(시간) 를 늘리는 방향의 비용은 큐비트 수가 아니라 **살아남는
파울리 항 수**가 지배하고, 이건 CPU 코어로 사는 게 아니라 **표현(비트패킹)과
절단 전략**으로 사야 합니다.

> **⚠️ 2026-08-31 추가 — 이 교훈을 "7×7 은 더 심하다" 로 읽으면 틀립니다.**
> 폭발하는 축은 `T` 이지 `n` 이 아닙니다. `T` 를 고정하면 광원뿔이 격자를
> 덮는 순간부터 격자를 키워도 항이 늘지 않습니다 (Lieb-Robinson). 중앙 사이트
> `X` 를 `T=0.5` 까지 전파한 실측 (노트북, dt=0.05, S4, δ=1e-5 — 절대값이
> 아니라 비율을 보는 조건):
>
> ```
> 3×3  9,945 → 4×4 29,405 → 5×5 55,434 → 6×6 56,606 → 7×7 58,593
>                  (×2.96)      (×1.89)      (×1.02)      (×1.04)
> ```
>
> **5×5~6×6 에서 포화합니다.** 모서리 사이트는 더 일찍입니다
> (940 → 1,187 → 1,195). 따라서 7×7 은 관측량 하나당 4×4 의 약 2배이고,
> 관측량이 32 → 98 로 3배이니 **T2 타겟 총비용 ≈ T1 의 6배** — numba 엔진이면
> 약 7시간입니다. **T2 는 감당 가능합니다.**
>
> 단서 둘. (a) 위는 δ=1e-5 이고 프로덕션은 1e-8 이라, 작은 계수가 더 오래
> 살아남으면 **포화 격자 크기가 커질 수 있습니다.** T2 착수 전에 프로덕션 δ 로
> 이 표를 다시 재세요. 정성적 결론(고정 `T` 에서 포화)은 광원뿔 논증이라
> 견고합니다. (b) **메모리는 별개입니다** — 7×7 전체가 대략 5천만 항이면
> 문자열 키로 ~10GB 이므로 비트패킹/numba 표현이 사실상 필수입니다. 즉 이
> 파일의 작업은 여전히 T2 의 선행 조건이지만, 이유가 "런타임이 불가능해서" 가
> 아니라 **"메모리가 안 맞아서"** 입니다.

**실전 채택**: `scripts/02b_time_sweep_parallel.py` 는 numba 엔진을 씁니다
(추가 배포 없이 검증됐고, 실측 스케일에서 이미 유의미하게 빠름). 정렬-배열
엔진은 코드베이스에 있고 (`propagation_sorted.py`) 항 수가 훨씬 커지는 국면
(7×7 이상, 또는 4×4 라도 largest 관측량이 매우 클 때)에서 다시 벤치마크할
가치가 있습니다.

## 2026-09-03 — GPU 재판정, 그리고 정렬병합에서 나온 60배

세션 질문: **"훈련 데이터 생성 / 훈련 / 비교 모델에서 GPU가 우위인가.
우위라면 4×4도 GPU로 돌리고 하드룰을 바꾼다."** 답은 워크로드마다 다르고,
답을 찾는 도중에 GPU와 무관한 더 큰 것이 나왔습니다.

### 먼저: `np.union1d` 가 엔진 비용을 지배하고 있었습니다

정렬배열 엔진(`propagation_sorted.py`)은 게이트마다 `xp.union1d` 를 한 번
부릅니다. numpy 2.5 의 `np.unique` — `union1d` 가 내부에서 부르는 것 — 이
**같은 일을 하는 sort+mask 보다 약 70배 느립니다.** 노트북 실측, uint64 배열:

| 원소 수 | `np.sort` | `np.unique` | 손으로 쓴 sort+mask |
|--:|--:|--:|--:|
| 600,000 | 4.88 ms | 231.95 ms | 5.02 ms |
| 2,400,000 | 19.80 ms | 1695.89 ms | 24.26 ms |

`int64` 로 view 해도 같습니다 (dtype 문제가 아님). 게이트 하나 비용에 그대로
얹혀 있었습니다:

| 항 수 | 기존 | `union1d` 제거 | + stable merge | |
|--:|--:|--:|--:|--:|
| 30,000 | 6.04 ms | 2.90 ms | 2.42 ms | **2.5배** |
| 300,000 | 132.52 ms | 41.65 ms | 38.95 ms | **3.4배** |
| 1,200,000 | 855.30 ms | 175.50 ms | 144.68 ms | **5.9배** |

`_union_sorted` / `_argsort` 로 고쳤습니다. **근사가 아니라 비트 단위로 같은
출력**입니다 — 무작위 20케이스에서 키 집합 완전 일치, 계수 최대편차 `0.0`
(1e-16 이 아니라 정확히 0), TEST 19 통과. stable 쪽은 `concatenate([commute,
union])` 이 이미 정렬된 두 런이라 timsort 가 O(N) 병합으로 처리한다는 것을
쓴 것이고, cupy 의 `argsort` 는 `kind` 를 안 받으므로 numpy 에서만 붙입니다.

`docs/issues/03` 위 표의 "정렬 배열 12.0s" 는 이 버그를 안고 잰 숫자입니다.
**7×7 진입 전에 다시 재야 합니다.**

### (a) 훈련 데이터 생성 — GPU 아니오, 그리고 더 분명해졌습니다

커널의 성질이 문제입니다. 게이트 하나가 **약 35개의 전체배열 호출**(정렬 2회,
이진탐색 2회)이고, 매 게이트마다 배열 shape 이 데이터에 따라 변하며, 14,000
개 게이트가 **순차 체인**이라 배칭이 불가능합니다 (게이트 k+1 의 입력이
게이트 k 의 출력). cupy 의 호출당 디스패치 오버헤드가 `35 × n_gates` 만큼
곱해진 뒤에야 산술이 시작됩니다.

2026-08-30 측정은 31.6K 항에서 cupy 가 numpy 에 **6.7배 졌습니다**. 그 CPU
쪽이 방금 3~6배 빨라졌으므로 격차는 **20배 수준으로 벌어집니다**. GPU 쪽에는
같은 수선거리가 없습니다 — `cupy.unique` 는 이미 sort+mask 입니다.

다만 그때 측정에는 별도의 결함이 하나 더 있었습니다: `propagate_forward_sorted`
는 `stats` 를 받으면 게이트마다 `float(xp.sum(coeffs ** 2))` 를 **두 번**
합니다. GPU 에서 이건 게이트당 두 번의 device→host 동기화라 파이프라인이 매번
비워집니다. 재측정할 때는 `stats=None` 이어야 합니다 (`03i_gpu_benchmark.py`
가 그렇게 합니다). 결론이 뒤집힐 것 같지는 않지만, 뒤집히지 않았다는 것을
깨끗하게 말하려면 이게 필요합니다.

### (b) 훈련 — GPU 는 지렛대가 아니고, 비용 자체가 알고리즘 실수였습니다

`BPPPSTrainer._time_evolution_step` 은 관측량마다 **파이썬 dict 루프**로 손실과
gradient seed 를 만듭니다. 그 루프의 두 번째 절이 문제였습니다:

```python
for P, a_target in target_spo.items():
    if P not in evolved:
        loss_g += a_target * a_target
```

**타겟 전체를 iteration 마다 훑습니다.** 그런데 타겟은 최적화 내내 고정이고,
`evolved` 는 짧은 안수가 만든 것이라 훨씬 작습니다 (타겟 120만 대 evolved 수천).
즉 매 스텝 O(|target|) 을 영원히 내고 있었습니다. 항등식 하나면 사라집니다:

```
sum_{P in target \ evolved} t_P^2  =  ||t||^2 - sum_{P in target ∩ evolved} t_P^2
```

`||t||^2` 는 생성자에서 한 번 계산하고(`_target_sq_norm`), 교집합 항은 이미
`t_P` 를 조회하고 있는 첫 루프에서 같이 누적하면 됩니다. 실측:

| 타겟 항 수 | evolved | 기존 | 수정 후 | |
|--:|--:|--:|--:|--:|
| 300,000 | 3,000 | 21.5 ms | 0.71 ms | 30배 |
| 1,200,000 | 3,000 | 92.4 ms | 0.77 ms | **120배** |

관측량 32개 × 1000 iteration 기준 **49분 → 25초**입니다. **근사가 아닙니다** —
2×2·3×3 에서 실제 생성한 타겟(3×3 은 936,200항)으로 기존 공식과 대조해 상대편차
`1e-14` 수준(합산 순서 차이)이고, **gradient 는 건드리지 않았습니다** (seed 는
원래부터 타겟 전용 문자열을 참조하지 않습니다 — 그것들의 evolved 계수에 대한
미분이 0이므로). 중심차분 대조 통과.

**GPU 와는 무관합니다.** 이건 파이썬 인터프리터 루프였고, 어떤 배열 백엔드도
손댈 수 없는 종류였습니다. 남은 훈련 비용은 짧은 안수(`L=3` 이면 120게이트)를
작은 SPO 에 통과시키는 전파인데, 그건 (a) 와 같은 커널이라 같은 이유로 GPU 가
아닙니다. 01·03이 이미 도달한 결론("스케일은 병렬화가 아니라 표현으로 산다")에
다른 경로로 도착했고, 이번에는 표현보다 **항등식**이 먼저였습니다.

### (c) 비교 모델 — **여기가 유일하게 GPU가 말이 되는 자리입니다**

`03_statevector_pilot.py` / `03f_gs_competitors.py` (Trotter, QAOA, 단열
Trotter) 는 파울리 전파가 아니라 **statevector** 입니다. 4×4 에서 2^16 진폭 ×
complex128 = 1.05 MB 이고, 게이트 하나가 고정 shape·분기 없는 elementwise
커널입니다. 정렬도 없고 데이터 의존 shape 도 없습니다 — (a) 와 모든 면에서
반대이고, 교과서적인 GPU 워크로드입니다.

이 스크립트는 성질이 다른 두 일을 합니다. **HVA·QAOA 는 최적화**이고
(`layers=[1,2,3,4,5,6,8,10,12]`, 시드 2개, 포인트당 `max_seconds=120`,
`maxiter=300`), **단열은 최적화가 아닙니다** — 각도가 스케줄로 고정돼 있고
60개 anneal time 을 훑어 제일 좋은 것을 고를 뿐입니다 (`evolve_only`, gradient
없음). 둘을 갈라 봐야 합니다.

**HVA·QAOA 쪽은 시간으로 잘려 있습니다.** `L≥8` 에서 300 iteration 에 닿지
못합니다 (노트북 실측, `apply_rzz` 수정 후):

| L | 2Q | gradient 1회 | 120초 안의 iteration |
|--:|--:|--:|--:|
| 2 | 48 | 224 ms | 535 |
| 3 | 72 | 282 ms | 425 |
| 5 | 120 | 394 ms | 304 |
| 8 | 192 | 589 ms | **204** |
| 10 | 240 | 730 ms | **164** |
| 12 | 288 | 918 ms | **131** |

즉 스윕의 위쪽 절반에서 L-BFGS 가 수렴 전에 잘립니다. 여기서의 처리량은 실행
시간을 줄이는 게 아니라 **경쟁 회로 곡선의 품질**을 삽니다 — 05-writing 이
목표 3의 유일한 병목으로 지목한 바로 그것입니다.

**단열 쪽은 이 프로젝트에서 유일하게 배칭이 되는 일입니다.** 60개 anneal time
이 서로 완전히 독립이라 데이터 의존이 없습니다. 전체 스윕은
`60 × 40 × Σ M(=466) = 1,118,400` 번의 게이트 적용, 게이트당 328µs 로 약 6분
입니다. 그런데 60개를 앞축으로 묶어 재 보면:

| M=24, anneal time 60개 | |
|:--|--:|
| 순차 | 18.9 s |
| 배치 (앞축 60) | **38.7 s (0.5배, 더 느림)** |

**CPU 에서는 배칭이 손해입니다.** 작업집합이 1 MB(L2 에 상주)에서 63 MB 로
커져 캐시를 벗어나기 때문입니다. 그리고 이게 정확히 GPU 논거입니다 — GPU 는
대역폭 律速이라 점유율을 채울 큰 배치를 원하고, 65,536 원소짜리 커널 하나는
런치 오버헤드에 묻힙니다. **CPU 를 느리게 만드는 바로 그 변형이 GPU 를 빠르게
만듭니다.** 프로젝트 전체에서 GPU 가 말이 되는 자리를 하나만 고르라면 여기,
단열 anneal-time 스캔입니다.

여기서도 공짜 CPU 수선이 먼저 있었습니다. `apply_rzz` 가 게이트마다 65,536개
복소수에 `np.exp` 를 부르고 있었는데, `pattern` 은 `±1` 만 담으므로
`exp(-i θ/2 p) = cos(θ/2) - i sin(θ/2) p` 로 **정확히** 같습니다. 게이트
1036µs → 162µs, gradient 전체 **1.8배**, 최대편차 `0.0`. 층마다 RZZ 가 40개 중
24개라 이게 큽니다. 고쳤고 `self_check()` (qiskit 대조 + parameter-shift
대조) 통과했습니다.

**GPU 기대치는 신중하게.** RTX 2060 은 Turing 이고 소비자용이라 FP64 가 FP32 의
1/32 입니다. complex128 산술은 FP64 입니다. 다만 이 커널은 대역폭 律速이지
FLOP 律速이 아니고(원소당 16바이트에 ~6 flop), 336 GB/s 를 채우려면 약 134
GFLOP/s 가 필요한데 2060 의 FP64 는 그와 비슷한 자릿수입니다. **대략 10배대를
기대하고 50배를 기대하지 마세요.** complex64 로 내리면 안 됩니다 — 지금 인용
중인 fidelity 들이 1e-7 자리입니다.
