## 32큐비트 초과 충돌 — 커밋된 데이터 하나가 무효입니다 (2026-09-04)

`x | (z << 32)` 는 33큐비트부터 단사가 아닙니다. `x` 가 비트 32를 쓰는데
거기가 `z` 의 비트 0 자리입니다:

```
Z_0  (x=0,      z=1) -> key = 2**32
X_32 (x=2**32,  z=0) -> key = 2**32      같은 키
```

두 엔진 모두 `d[key] = value` 로 씁니다. 즉 **덮어쓰기**이고, 서로 다른 파울리
항 하나가 소리 없이 사라집니다. 항 수는 과소계수되고 살아남은 계수는 엉뚱한
문자열의 것입니다. 예외도 경고도 없고 숫자는 그럴듯해 보입니다.

**실제로 발동했는지 측정했습니다.** 같은 6×6 전파를 **문자열 엔진**(팩킹이
없으니 충돌도 없음)으로 더 느슨한 절단에서 다시 돌렸습니다:

| δ | 항 수 | 닿은 최대 큐비트 | 인덱스 ≥32 에 지지를 가진 항 |
|--:|--:|--:|--:|
| 1e-3 | 522 | **33** | 42 |
| 1e-4 | 6,806 | **34** | 1,214 |

느슨한 δ 는 항을 **더 적게** 남기므로, 프로덕션 δ=1e-8 은 반드시 여기 닿습니다.
**따라서 `results/lightcone_production_delta.json` 의 `L=6` 행(36큐비트)은
무효입니다.** `L=3·4·5`(9·16·25큐비트)는 한계 안이라 그대로 유효합니다.

**대가가 정확히 어디에 걸리는지가 나쁩니다.** 포화 주장의 근거가 그 행
하나였습니다 — `ratio_vs_prev` 가 48.33 (3→4), 5.13 (4→5), **0.988 (5→6)**
이고 "포화"라고 말하는 건 0.988 뿐입니다. 게다가 오염 방향이 **과소계수**라
비율을 **아래로** 밀어, 하필 내려진 결론 쪽으로 편향시킵니다. 살아남는 것은
감속(48.3 → 5.13)이고, 이건 포화에 접근 중이라는 것과 **양립하지만 증명하지는
않습니다.** T2 비용 추정을 여기 기대면 안 됩니다.

**막은 방법.** 키 생성 진입점을 막는 건 소용이 없습니다 — 단일 사이트 관측량은
비트가 하나뿐이라 언제나 통과하고, numba 는 이후 모든 키를 `@njit` 루프 안에서
원시 비트연산(`Rkey = (x ^ kbit) | (z << 32)`)으로 만들어 `make_key()` 를 다시
안 거칩니다. 그래서 검사를 **게이트 시퀀스**에 걸었습니다
(`propagation_packed.check_gate_sequence_packable`): 회로가 건드리는 최대 큐비트
인덱스는 전파가 시작되기 *전에* 알 수 있는 유일한 양입니다. `propagate_forward_numba`,
`propagate_forward_sorted`, `propagate_backward_sorted` 세 진입점 전부에서 호출하고,
비용은 120게이트 시퀀스 기준 **3.8 µs**(gradient 1회가 ~6초)입니다. **TEST 22** 가
회귀 테스트입니다.

### 두 번째 가드 — 키 생성 쪽 (노트북에서 독립으로 만들어진 것)

위 게이트 시퀀스 검사와 **별개로** 키 생성 경로에도 가드가 들어갔습니다. 두
기계가 같은 문제를 각각 풀었고, 합쳐 보니 **중복이 아니라 상보적**입니다.

| | 무엇을 검사 | 어디서 | 테스트 |
|:--|:--|:--|:--|
| `check_gate_sequence_packable` | 회로가 건드리는 최대 큐비트 인덱스 | `@njit` 루프 시작 **전** | TEST 22 |
| `assert_key_width` / `pack_key` / `to_sorted_arrays` | 큐비트 수 / 항 하나 / SPO 전체(벡터화 max 한 번) | 키를 **만들 때** | TEST 23 |

전자만으로는 게이트 시퀀스를 거치지 않고 직접 만들어진 SPO 가 안 걸리고,
후자만으로는 numba 가 루프 안에서 원시 비트연산으로 만드는 키가 안 걸립니다.
**둘 다 필요합니다.** 실측하면 `x=z=1<<40` 이 `0x10000000000` 으로 가서,
**z 가 uint64 밖으로 통째로 밀려나** z 가 다른 모든 파울리가 한 키에 뭉치고
계수가 조용히 합쳐졌습니다.

## 키 폭 확장 — `propagation_wide.py` (2026-09-04)

위의 가드들은 7×7·10×10 을 **거부**합니다. 이 모듈이 그것을 **받습니다.**
`CLAUDE.md` 하드룰 4의 "7×7 은 키를 먼저 넓혀야 한다" 가 여기서 해소됩니다.

**표현.** SPO 를 `(N, 2W)` uint64 행렬로 듭니다 — x 마스크 `W` 워드 뒤에 z
마스크 `W` 워드, `W = ceil(n/64)`. 49큐비트는 마스크당 1워드, 100큐비트는 2워드.

**왜 dtype 을 넓히는 대신 새 모듈인가.** 64비트 커널은 키의 옛 계수를
`searchsorted` 로 찾는데, **searchsorted 에는 다중열 형태가 없습니다.** numpy
의 structured dtype 은 사전식 정렬이 되지만 **cupy 가 정렬하지 못하고**, 큰 `n`
워크로드가 정확히 GPU 를 원하는 곳입니다. 그래서 lookup 자체를 없앴습니다.

**없앨 수 있는 이유 (사실 셋, 각각 64비트 엔진과 대조 확인).**

- **A.** `union & keys == anti_keys`. 합집합은 {anti 키} ∪ {그 파트너}인데,
  파트너는 게이트가 검사하지 *않는* 좌표에서만 다르므로(RX 는 x 를 뒤집고 z 를
  검사, RZZ 는 z 를 뒤집고 x 를 검사) 파트너도 반교환합니다. → `old_self` 는
  anti 키 위에서만 0이 아니고, 그 계수는 이미 손에 있습니다.
- **B.** 합집합은 파트너 뒤집기에 닫혀 있습니다. `(A ∪ A^f)^f = A^f ∪ A`.
- **C.** `old_partner == old_self[argsort(union ^ flip)]`.

남는 연산은 정렬·argsort·XOR·동등비교뿐이고, 전부 **LSD 기수정렬**(열마다 안정
argsort, 최하위부터)과 행 단위 `==` 로 행렬 키에 확장됩니다. numpy 와 cupy
양쪽에서 됩니다.

**대가.** 정렬 한 번에 안정 argsort 가 `2W` 번 필요합니다(팩킹 엔진은 1번).
**둘 다 되는 `n` 에서는 항상 이쪽이 느립니다.** 속도로 고르지 마세요 —
`pick_kernel(n)` 이 `n ≤ 32` 면 `'packed'`, 아니면 `'wide'` 를 돌려주고,
`TargetGenerator` 가 그걸 씁니다. 손으로 고르는 것이 조용한 충돌을 출하하는
경로였습니다.

**검증.** **TEST 24** 가 문자열 오라클과 항 단위로 대조합니다. 창(window)이
항 수보다 중요합니다 — 100큐비트에 무작위 회로를 흩뿌리면 SPO 가 두어 항에
머물러 아무것도 증명하지 못합니다. 그래서 표현이 깨질 수 있는 자리에 좁은
지지를 놓습니다: 큐비트 32(팩킹 키의 벽)를 걸치는 창, 32 위쪽만, 큐비트
64(이 모듈의 워드 경계)를 걸치는 창, 상위 워드 안쪽만.

⬜ **아직 안 한 것: 성능 측정.** `2W` 배 argsort 의 실제 비용과 7×7 타겟 생성
예산을 재지 않았습니다. T2 착수 전에 `2-0` 형태의 벤치마크가 필요합니다.

## 타겟 생성 — 엔진은 5~15배 남았지만 그게 벽이 아닙니다 (2026-09-04)

### 그런데 `T=1.0` 은 여전히 안 열립니다 — 벽은 엔진이 아니라 항 수입니다

`X_9` 의 k=1 SPO(293,198항)를 **정렬 엔진**으로 블록 하나 더 통과시키는 중간

게이트당 속도의 문제가 아닙니다. `T`=2.0(k=4)은 이게 두 번 더 복리로 붙습니다.

### 프로덕션 `δ` 로 다시 잰 빛원뿔 (2026-09-03 실행, 여기 처음 기록)

`scripts/03h_lightcone_production_delta.py` → `results/lightcone_production_delta.json`.
`δ=1e-8`, `T=0.5`, `dt=0.05`, 4차 Trotter. **관측량 하나**(중앙 사이트)를 전파한 값:

| 격자 | 중앙 항 수 | 직전 대비 | 모서리 항 수 | 소요 |
|:--|--:|--:|--:|--:|
| 3×3 | 58,068 | — | 21,166 | 7.7 s |
| 4×4 | 2,806,148 | ×48.3 | 72,256 | 822 s |
| 5×5 | 14,387,115 | ×5.13 | 81,202 | 6,942 s |
| 6×6 | 14,207,863 | **×0.99 ← 포화** | 81,096 | 9,153 s |
| 7×7 | **미측정** | | | 실행이 6×6 에서 멈춤 |

**좋은 소식:** 포화는 프로덕션 `δ` 에서도 성립합니다 (6×6/5×5 = 0.99).
`δ` 를 조이면 포화 격자 크기가 커질 수 있다는 우려는 **기각**됐습니다 —
`δ=1e-5` 때와 같은 5×5~6×6 에서 포화합니다. 모서리 사이트는 훨씬 이르게,
훨씬 작은 값(8만 대 1,400만, **175배 차이**)에서 포화합니다.

**나쁜 소식 셋:**

1. **절대 규모가 250배입니다.** `δ=1e-5` 의 6×6 이 56,606 항이었는데
   `δ=1e-8` 에서는 14,207,863 항입니다.
2. **관측량 하나에 2.5시간**이고 7×7 은 관측량이 **98개**입니다. 중앙부
   관측량이 비용을 지배하므로 총비용을 다시 추정해야 합니다 — 단순 곱은
   과대추정입니다(모서리가 175배 쌈).
3. **7×7 을 못 쟀습니다.** `sizes=[3,4,5,6,7]` 로 요청했는데 6×6 에서 멈췄고,
   `mem_floor_gb=3.0` 가드가 걸린 것으로 보입니다. **7×7 의 절대 비용은 아직
   측정값이 아닙니다.**

**T2 진입 전에 할 일:** (a) 7×7 을 비트패킹 엔진으로 다시 시도해 실제 항 수와
메모리를 확정, (b) 98개 관측량의 비용 분포(중앙 대 모서리)로 총비용 재추정.

전환 시 결정할 것:

- `n > 64` 처리 (10×10 은 100큐비트 → `uint64` 두 쌍 또는 구조화 dtype).
  **정렬 엔진의 32큐비트 한계를 먼저 푸는 것이 같은 문제입니다.**
- Julia 쪽 표현을 맞출지
- **등가성 검증은 4×4 에서.** 두 엔진의 계수를 항 단위로 비교할 수 있는
  마지막 규모입니다 (TEST 17~22 가 하는 일)

## 2026-09-04 — 문자열 dict 를 마지막 남은 곳에서 걷어냈습니다

훈련은 `f918ac7` 에서 이미 옮겨갔지만 **타겟 생성은 아직 오라클 엔진이었습니다.**
프로젝트에서 가장 비싼 단계가(4×4 관측량 하나 822초, 5×5 하나 2.5시간) 가장
느린 엔진 위에 있었던 셈입니다.

### 1. 패킹 키 단사 — 이제 소리를 냅니다

가드가 **하나도 없었습니다.** 세 곳이 각자 `x | (z << 32)` 를 직접 만들고
있었고(`to_sorted_arrays`, `trainer._packed_keys`, `trainer._sorted_setup`),
어디에도 폭 검사가 없었습니다. 실측한 실패 형태:

```
x = z = 1<<40  ->  키 0x10000000000     # z 가 uint64 밖으로 통째로 밀려남
```

즉 33큐비트 위에서는 **z 가 다른 파울리들이 전부 같은 키**가 되고, 계수가
말없이 합쳐지고, 그 뒤 모든 결과가 틀립니다. 예외도 경고도 없이.

고친 방식: 패킹을 `propagation_sorted.pack_key` 한 곳으로 모으고, 세 층위에서
막습니다 — `assert_key_width(n)`(설정 시점, O(1)), `pack_key(x, z)`(항 하나),
`to_sorted_arrays`(SPO 전체를 벡터화 `max()` 한 번으로). 트레이너와 타겟
생성기가 셋업에서 `assert_key_width` 를 부르므로 **7×7 은 몇 시간 뒤가 아니라
시작하자마자 멈춥니다.** TEST 23 이 고정합니다.

부수적으로 `to_sorted_arrays` 가 빨라졌습니다. 1.2M 항짜리 타겟을 파이썬
`sorted()` 로 튜플 정렬하던 것을 `np.fromiter` + `argsort` 로 바꿨습니다.

### 2. 타겟 생성이 정렬 엔진으로

`TargetGenerator(engine=...)` — `'string'` | `'sorted'` | `'gpu'`.
`generate()` 와 `generate_series()` 둘 다. 설정은 `target.engine`(`ansatz_ibm.yaml`)
과 `time_sweep.engine`(`time_sweep.yaml`), **기본값 `sorted`**.

문자열 오라클과 대조 (`generate()` 전체, 모든 관측량):

| 격자 | 항 수 | support 차이 | 최대 계수편차 | 문자열 | 정렬 | |
|:--|--:|--:|--:|--:|--:|--:|
| 2×2 | 472 | 0 | **0.000e+00** | 0.11 s | 0.31 s | 0.4배 (교차점 아래) |
| 3×3 | 500,154 | 0 | **0.000e+00** | 166.7 s | 19.9 s | **8.4배** |

**항 단위로 같습니다.** 4×4 프로덕션은 관측량당 280만 항이라 3×3 보다 더
위쪽이고, GPU 는 그보다 더 위(120만 항에서 17.3배)입니다.

### 3. GPU 경로의 동기화 병목을 먼저 치웠습니다

`propagate_forward_sorted` 는 `stats` 를 받으면 게이트마다
`float(xp.sum(coeffs**2))` 를 **두 번** 했습니다. cupy 에서 이건 게이트당 두 번의
device→host 동기화라, 14,000 게이트짜리 타겟 청크 하나에 **28,000번** 파이프라인이
비워집니다. 하필 GPU 를 가장 원하는 워크로드에서요. 그런데 타겟 생성은 `stats`
가 필요합니다(`eps_trunc` 가 결과에 실립니다).

고쳤습니다: 누적을 0-d 디바이스 배열로 두고 **끝에서 한 번만** 변환하고, 각
게이트의 출력 노름을 다음 게이트의 입력 노름으로 이어받아 리덕션 수도 절반으로
줄였습니다. **numpy 에서 옛 경로와 비트 단위로 동일**합니다 — 4개 케이스에서
`eps_trunc` 차이가 정확히 `0.000e+00`, 키·계수 배열도 `array_equal`.

### ⚠️ 다만 `eps_trunc` 는 엔진마다 다릅니다 (이전부터)

SPO 는 항 단위로 같지만 **절단 추정치는 같지 않습니다.** 문자열 엔진은 버리는
항을 항별로 누적하고, 배열 엔진은 게이트마다 노름 차분으로 잡습니다:

| | 문자열 | 정렬 |
|:--|--:|--:|
| 2×2, `eps~1e-7` | 3.541e-07 | 6.726e-07 (**2배**) |
| 3×3, `eps~1e-5` | 1.473644e-05 | 1.473457e-05 (4자리 일치) |

원인은 상쇄입니다 — 노름 차분은 `1.0 - 1.0` 에서 `1e-10` 을 뽑는 계산이라,
버려진 총 노름이 작을수록 유효숫자가 남지 않습니다. **`eps_trunc` 가 `1e-6`
아래로 내려가는 영역에서는 배열 엔진의 추정치를 자릿수 이상으로 믿지 마세요.**
적응적 절단(`adaptive_delta`)이 이 값을 쓰므로 관련이 있습니다. 훈련은
`f918ac7` 이후 이미 이 상태였으니 새로 생긴 문제는 아닙니다.

### Julia 는 지금 답이 아닙니다

열린 질문의 "비트패킹 전환을 Python 에서 할지 Julia 로 넘어갈지" 에 대한 답:
**Python 으로 충분합니다.** 정렬 엔진의 게이트당 비용은 이제 파이썬이 아니라
numpy 의 C 정렬·이진탐색 안에 있습니다. Julia 가 이길 여지는 커널을 더 잘 쓰는
것뿐인데, 파이프라인 전체가 Python 이고 `model_config.json` 계약을 하나 더
유지해야 합니다. **Julia 를 다시 꺼낼 이유는 속도가 아니라 키 확장입니다** —
`UInt128` 이 네이티브라 아래 문제가 거기서는 없습니다.

### 다음 관문은 키 폭입니다

이제 4×4·5×5 는 전 구간이 배열 엔진 위에 있고, **7×7 을 막는 것은 속도가 아니라
32큐비트 키**입니다. 설계 메모: 지금 `_lookup` 이 `searchsorted` 를 쓰는데,
이것이 128비트 키로 넘어가는 걸 어렵게 만드는 유일한 부분입니다 (구조화
dtype 은 cupy 가 정렬을 지원하지 않습니다). 피할 수 있습니다 —
`union = anti ∪ (anti^flip)` 은 flip 에 대해 닫혀 있고 `union ∩ keys = anti`
이므로, `old_partner = old_self[argsort(union ^ flip)]` 이고 `old_self` 는
union 을 만들 때의 argsort 에서 바로 나옵니다. **그러면 커널이 `sort`/`argsort`
와 동등 비교만 쓰게 되고, 둘 다 안정 정렬 두 번(LSD 기수)으로 2열 키에 그대로
확장됩니다 — numpy 와 cupy 양쪽에서.** 아직 구현하지 않았습니다.
