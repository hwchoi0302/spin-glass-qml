## 32큐비트 초과 충돌 — 커밋된 데이터 하나가 무효입니다 (2026-09-04)

`x | (z << 32)` 는 33큐비트부터 단사가 아닙니다. `x` 가 비트 32를 쓰는데
거기가 `z` 의 비트 0 자리입니다:

```
Z_0  (x=0,      z=1) -> key = 2**32
X_32 (x=2**32,  z=0) -> key = 2**32      같은 키
```

두 엔진 모두 `d[key] = value` 로 씁니다. 즉 **덮어쓰기**이고, 서로 다른 파울리
항 하나가 소리 없이 사라집니다. 항 수는 과소계수되고 살아남은 계수는 엉뚱한
문자열의 것입니다. 예외도 경고도 없고 숫자는 그럴듯해 보입니다.

**실제로 발동했는지 측정했습니다.** 같은 6×6 전파를 **문자열 엔진**(팩킹이
없으니 충돌도 없음)으로 더 느슨한 절단에서 다시 돌렸습니다:

| δ | 항 수 | 닿은 최대 큐비트 | 인덱스 ≥32 에 지지를 가진 항 |
|--:|--:|--:|--:|
| 1e-3 | 522 | **33** | 42 |
| 1e-4 | 6,806 | **34** | 1,214 |

느슨한 δ 는 항을 **더 적게** 남기므로, 프로덕션 δ=1e-8 은 반드시 여기 닿습니다.
**따라서 `results/lightcone_production_delta.json` 의 `L=6` 행(36큐비트)은
무효입니다.** `L=3·4·5`(9·16·25큐비트)는 한계 안이라 그대로 유효합니다.

**대가가 정확히 어디에 걸리는지가 나쁩니다.** 포화 주장의 근거가 그 행
하나였습니다 — `ratio_vs_prev` 가 48.33 (3→4), 5.13 (4→5), **0.988 (5→6)**
이고 "포화"라고 말하는 건 0.988 뿐입니다. 게다가 오염 방향이 **과소계수**라
비율을 **아래로** 밀어, 하필 내려진 결론 쪽으로 편향시킵니다. 살아남는 것은
감속(48.3 → 5.13)이고, 이건 포화에 접근 중이라는 것과 **양립하지만 증명하지는
않습니다.** T2 비용 추정을 여기 기대면 안 됩니다.

**막은 방법.** 키 생성 진입점을 막는 건 소용이 없습니다 — 단일 사이트 관측량은
비트가 하나뿐이라 언제나 통과하고, numba 는 이후 모든 키를 `@njit` 루프 안에서
원시 비트연산(`Rkey = (x ^ kbit) | (z << 32)`)으로 만들어 `make_key()` 를 다시
안 거칩니다. 그래서 검사를 **게이트 시퀀스**에 걸었습니다
(`propagation_packed.check_gate_sequence_packable`): 회로가 건드리는 최대 큐비트
인덱스는 전파가 시작되기 *전에* 알 수 있는 유일한 양입니다. `propagate_forward_numba`,
`propagate_forward_sorted`, `propagate_backward_sorted` 세 진입점 전부에서 호출하고,
비용은 120게이트 시퀀스 기준 **3.8 µs**(gradient 1회가 ~6초)입니다. **TEST 22** 가
회귀 테스트입니다.

## 훈련이 정렬 엔진으로 옮겨갔습니다 (`f918ac7`)

실제 워크로드(`X_5`, 프로덕션 `L=3` 각도, δ=1e-6, 396,896항) 기준:

| 엔진 | 순전파 | 비고 |
|:--|--:|:--|
| 문자열 dict | 8.72 s | 옛 기본값 |
| numba | 1.29 s | 6.8배 |
| **정렬 numpy** | **0.50 s** | **17.3배** |
| 정렬 cupy | 0.53 s | 이 규모에서는 numpy 와 무승부 |

역전파까지 합쳐 **18.2배**입니다 (순전파 14.6배, 역전파 20.3배). 역전파가 더

문자열 엔진의 Adam 만 10~14시간이던 것과 비교됩니다. **에폭별 손실은 자릿수까지
동일**합니다.

> 정렬한 뒤 키를 `x | (z << 32)` 로 만들었는데 두 순서가 다릅니다. 정렬 안 된
> 배열을 돌려줘서 하류의 모든 `searchsorted` 가 틀린 슬롯을 읽고 있었습니다.
> 유일한 호출자가 항 하나짜리 `self_check()` 라 TEST 19·20 이 못 잡았습니다.
> **TEST 21** 이 역전파를 문자열 엔진과 중앙차분 양쪽에 고정합니다.

## GPU — 2026-08-30 판정은 틀렸습니다 (`1d6fe37`)

**이 파일의 이전 판은 "이 커널은 GPU 대상이 아니다" 라고 결론지었습니다.
그건 CPU 경쟁 상태에서 42분 만에 중단된 측정이었습니다.** 한가한 데스크탑에서
다시 재니 **세 파트 모두 GPU 가 이깁니다** (`gpu_benchmark.json`).

| 파트 | 무엇 | 결과 |
|:--|:--|:--|
| A | 파울리 전파, 정렬 엔진 | **교차점이 10만 항 근처.** 30K 0.23× / 100K 1.97× / 300K 12.3× / **1.2M 17.3×** |
| B1 | HVA·VQE adjoint gradient | **3.5~6.6×.** `L=3` 에서 120초에 163 → 1037 iteration |
| B2 | 단열 anneal-time 스캔 (60겹 배치) | **5.4~5.8×.** CPU 배칭은 0.5배 **손해**, GPU 에선 그게 요점 |
| C | 훈련 항등식 수정 재확인 | 15~138×, 손실 편차 ≤ 4.6e-14 |

**따라서 닫혀 있던 항목이 둘 다시 열립니다.**

1. **T1-T stage 1 재시도.** 취소 사유였던 관측량(`X_6`/`X_10`)이 1.23M 항이고,
   그 구간이 정확히 GPU 17.3배입니다. 교차점 위에 한참 있습니다.
2. **`03f_gs_competitors.py` 백엔드 일반화.** B1 이 사는 것은 실행 시간이 아니라
   **수렴**입니다 — 지금 `L≥3`, `p≥8` 이 전부 시간 상한에 걸려 있어서 경쟁자와
   우리 곡선의 깊은 점이 미수렴 상태입니다.

> **libcublas 함정.** 이 기계의 site-packages 에는 torch 의 CUDA 13 휠이 있어
> `cupy-cuda12x` 가 `libcublas.so.12` 를 못 찾고 파트 B 가 `xp.vdot` 에서
> 죽습니다. CUDA 12 휠을 `~/.local/cuda12-libs` 에 따로 깔고
> `scripts/cuda12_env.sh` 가 torch 쪽을 가리지 않으면서 `LD_LIBRARY_PATH` 에

## 타겟 생성 — 엔진은 5~15배 남았지만 그게 벽이 아닙니다 (2026-09-04)

`TargetGenerator` 는 아직 **문자열 엔진**을 씁니다 (`target_generator.py:93`,
`:175`). 훈련만 정렬 엔진으로 옮겨갔고 타겟 생성은 그대로였습니다. 실제
프로덕션 블록(dt=0.001, S4, 140,000 게이트)에서 커밋된 k=1 SPO 를 출발점으로
400 게이트를 재봤습니다 (한가한 머신):

| 관측량 | k=1 항 수 | 문자열 ms/게이트 | 정렬 ms/게이트 | 정렬이 |
|:--|--:|--:|--:|--:|
| `Z_15` | 2,636 | 1.03 | 0.21 | 4.8배 빠름 |
| `Z_0` | 2,677 | 1.36 | 0.17 | 8.1배 |
| `X_0` | 8,455 | 3.10 | 0.32 | 9.6배 |
| `X_5` | 292,418 | 267.77 | 18.33 | 14.6배 |
| `X_9` | 293,198 | 262.22 | 17.16 | **15.3배** |

**작은 관측량에서 손해 보는 구간은 없습니다.** "3만 항에서 0.23배" 는
`gpu_benchmark.json` 의 **cupy 대 numpy** 행이지 정렬 대 문자열이 아닙니다.
둘을 섞으면 안 됩니다.

### 그런데 `T=1.0` 은 여전히 안 열립니다 — 벽은 엔진이 아니라 항 수입니다

`X_9` 의 k=1 SPO(293,198항)를 **정렬 엔진**으로 블록 하나 더 통과시키는 중간
경과(k=2 = `T`=1.0 타겟):

| 진행 | 항 수 | ms/게이트 | 누적 |
|--:|--:|--:|--:|
| 20,000 / 140,000 | 654,035 | 41.7 | 834 s |
| 40,000 / 140,000 | 1,679,345 | 107.6 | 2,986 s |
| 60,000 / 140,000 | **2,693,331** | **314.4** | **9,274 s** |

게이트당 비용이 초선형으로 오릅니다(×2.6, ×2.9). **관측량 하나가 43% 지점에서
이미 2.6시간**이고, 남은 80,000 게이트는 314 ms/게이트로만 잡아도 25,000초
추가 — 즉 `X_9` 하나에 **9.5시간이 하한**이고 실제로는 더 듭니다. 관측량은
32개입니다.

정렬 엔진은 이걸 "불가능"에서 "여전히 비현실적"으로 옮겼을 뿐입니다.
**T1-T stage 1 을 취소했던 진단이 옳았습니다** — 표현/절단 차원의 문제이지
게이트당 속도의 문제가 아닙니다. `T`=2.0(k=4)은 이게 두 번 더 복리로 붙습니다.

### GPU 는 실제 워크로드에서 3.6배지 17배가 아닙니다

같은 `X_9` 출발점, 같은 코드, `xp` 만 교체 (RTX 2060, 5.0 GB 여유, 두 엔진의
항 수 일치 확인):

| 게이트 | numpy | cupy | GPU |
|--:|--:|--:|--:|
| 200 | 3.48 s | 0.93 s | 3.7배 |
| 800 | 14.32 s | 3.94 s | 3.6배 |

`gpu_benchmark.json` 파트 A 는 같은 항 수(30만)에서 **12.3배**를 말합니다.

## 비트패킹 (7×7 진입 조건)

BP-PPS 논문 Appendix C. 파울리 문자열을 정수 두 개(X 마스크, Z 마스크)로 담고
교환 판정 = popcount, 부호 = 마스크 AND/XOR, 해시 = 정수 둘.

**7×7 의 벽은 런타임이 아니라 메모리입니다** — 5천만 항 ≈ 10GB. 타겟 생성
비용 자체는 T1 의 6배(약 7시간)로 감당 가능합니다.

전환 시 결정할 것:

- `n > 64` 처리 (10×10 은 100큐비트 → `uint64` 두 쌍 또는 구조화 dtype).
  **정렬 엔진의 32큐비트 한계를 먼저 푸는 것이 같은 문제입니다.**
- Julia 쪽 표현을 맞출지
- **등가성 검증은 4×4 에서.** 두 엔진의 계수를 항 단위로 비교할 수 있는
  마지막 규모입니다 (TEST 17~21 이 하는 일)

지금 JSON, 364MB/스냅샷, 파싱이 느립니다. 비트패킹으로 가면 자연스럽게

## Julia 엔진

- `PauliPropagation.jl` 은 **선택적 의존성**입니다 (`Project.toml` 의 `[deps]`
  에 없고 `HAS_PAULI_PROPAGATION` 가드로 감쌈). 실제 훈련은
  `julia/src/bppps_engine.jl` 의 자체 구현이 합니다.
- 데스크탑에서 Julia 를 처음 쓸 때 `julia/scripts/check_env.jl` 를 먼저.
- **Julia 는 커플링을 재생성하지 않습니다.** `model_config.json` 을 읽고 본드
  순서를 검증만 합니다. 예전에 Python 은 `for x, y`, Julia 는 `for y, x` 로
  수직 본드를 열거해 **두 파이프라인이 다른 모델을 풀고 있었습니다.**

## 열린 질문

- **정렬 키를 32큐비트 위로 넓히는 방법.** 7×7 진입의 첫 관문이고, 비트패킹
  `n>64` 문제와 같은 결정입니다.
- **훈련을 GPU 로 옮길지.** 지금 훈련 규모(약 40만 항)는 교차점 바로 위라
  numpy 와 cupy 가 무승부입니다. 7×7 로 가면 항 수가 그 위로 올라가므로
  **T2 진입과 함께 다시 재야 합니다.**
- **T1-T stage 1 을 GPU 로 재시도할지.** 위 판정 뒤집힘의 직접적 결과입니다.
  되면 `T>0.5` 훈련이 열리고 "깊이가 `T` 에 선형인가" 에 처음으로 답합니다.
- 비트패킹 전환을 Python 에서 할지 Julia 로 넘어갈지. Julia 가 이런 커널에
  자연스럽지만 파이프라인 전체가 Python 입니다.
- 적응적 절단이 시간 스윕에서 실제로 도움이 되는지.

> **`propagation_gpu.py` 는 존재한 적이 없습니다.** GPU 경로는 별도 모듈이
> 아니라 `propagation_sorted` 에 `xp=cupy` 를 넘기는 것이고 TEST 20 이 그걸
> 합니다. 옛 docstring 두 곳의 참조는 고쳤습니다.
