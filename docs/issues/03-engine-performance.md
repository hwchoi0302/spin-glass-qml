# 03 — 엔진과 성능

담당 범위: Pauli propagation 엔진의 표현·속도·메모리. **7×7 진입 전에 반드시
처리해야 하는 항목들**이 여기 있습니다.

## 왜 지금 중요한가

4×4 T1-T stage 1의 k=1 스냅샷만으로 이미:

```
n_terms 8,304,835   largest_observable 1,239,943   targets_k1.json 364MB
```

문자열 키 dict 기준 항당 대략 190바이트 → 8.3M 항이 ~1.6GB. **49큐비트에서는
현재 표현으로 못 갑니다.**

## 비트패킹 (7×7부터, 4×4는 그대로)

BP-PPS 논문 Appendix C. 파울리 문자열 `P ∈ {I,X,Y,Z}^n` 을 문자열이 아니라
정수 두 개(X 마스크, Z 마스크)로 담습니다. n=49면 각각 `uint64` 하나, 즉 항 하나가
16바이트 + 계수 8바이트입니다. 문자열 dict 대비 열 배 이상 줄고, 더 중요하게는
**게이트 적용이 비트 연산**이 됩니다:

- 교환 여부 판정 = popcount 한 번
- 부호 = 마스크 AND/XOR
- 해시 = 정수 두 개

현재 `src/bppps/propagation.py` 는 `Dict[str, float]` 입니다. 전환 시 결정할 것:

- n > 64 를 처리할 방법 (10×10은 100큐비트 → `uint64` 두 쌍, 또는 numpy `uint64`
  배열 + 구조화 dtype)
- dict 를 유지할지, 정렬 배열 + 병합으로 갈지. 후자가 캐시 지역성이 훨씬 좋고
  벡터화가 되지만 코드가 커집니다
- Julia 쪽(`julia/src/bppps_engine.jl`)과 표현을 맞출지

**등가성 검증은 4×4에서** 해야 합니다 — 두 엔진이 같은 입력에 같은 계수를
내는지 비교할 수 있는 마지막 규모입니다.

## 타겟 캐시 형식

지금은 JSON입니다. 364MB/스냅샷이고 파싱이 느립니다. 비트패킹으로 가면 자연스럽게
`npz` 또는 `hdf5` (마스크 배열 + 계수 배열) 로 갑니다. 이건 비트패킹과 같은
작업으로 묶는 게 맞습니다.

## Julia 엔진

- `PauliPropagation.jl` 은 **선택적 의존성**입니다. `julia/Project.toml` 의
  `[deps]` 에서 뺐고, `HAS_PAULI_PROPAGATION` 가드로 감쌌습니다. 실제 훈련은
  `julia/src/bppps_engine.jl` 의 자체 구현이 합니다.
- `julia/scripts/check_env.jl` 가 엔진, 모델 계약, PauliPropagation API 를
  검증합니다. 데스크탑에서 Julia를 처음 쓸 때 이걸 먼저 돌리세요.
- **Julia는 커플링을 재생성하지 않습니다.** `model_config.json` 을 읽고 본드
  순서를 검증만 합니다. 예전에 Python은 `for x, y`, Julia는 `for y, x` 로 수직
  본드를 열거해 두 파이프라인이 다른 모델을 풀고 있었습니다.

## 열린 질문

- 비트패킹 전환을 Python에서 할지 Julia로 넘어갈지. Julia가 이런 커널에는
  자연스럽지만, 파이프라인 전체가 Python에 있습니다.
- 정렬 배열 병합 방식이 dict 대비 실제로 얼마나 빠른지 — 측정해야 합니다.
- 적응적 절단(adaptive truncation)이 시간 스윕에서 실제로 도움이 되는지.
  T1-T stage 4의 δ 스윕이 근거를 줍니다.
- **병렬화·GPU 는 아직 손도 대지 않았습니다.** Python `propagation.py` 도 Julia
  `bppps_engine.jl` 도 단일 스레드 `Dict{String,Float64}` 입니다. 데스크탑
  Ryzen 5 5600 은 6코어/12스레드인데 항상 1코어만 씁니다. 순서는
  ① 비트패킹(`UInt64` 키) → ② 스레드 병렬 → ③ GPU 입니다. GPU를 먼저 보면 안
  되는 이유는, 지금 커널이 문자열 해시맵 삽입이라 GPU로 옮길 대상 자체가
  아니기 때문입니다. 정렬 기반 병합으로 바꾼 뒤에야 GPU가 의미를 가집니다.
  (01 세션에서 나온 질문. 자세한 근거는 `01-scale-plan.md` 의 "왜 CPU만 쓰나".)

## 2026-08-30 자율 세션 — 목표와 순서

사용자가 잠들기 전 승인한 범위. 순서대로 진행하고 각 단계를 커밋합니다.
메모리는 **실시간 감시**. `.wslconfig` 로 WSL 캡을 11GB → 19GB(가용 17GB)로
올림 (사용자가 직접, `wsl --shutdown` 후 세션 재개). 17GB 기준으로 진행.

1. **statevector pilot** (`scripts/03_statevector_pilot.py`, 신규) — 손으로 짠
   RX/RZZ statevector applier로 (a) 목표1/T1-T: T={0.5,1,2,4} × layers
   [2,3,4,6,8] 직접 훈련 하한, (b) 목표3: 바닥상태 ceiling-vs-layers
   (L=1..8). 타겟 캐시·절단 불필요, 둘 다 ED 대조. 예상 ~1시간.
2. **T1-T stage 1 병렬화** — 기존 `propagation.py`/`target_generator.py` 는
   건드리지 않고 (검증된 오라클), 새 오케스트레이션 스크립트가 32개 관측량을
   `multiprocessing.Pool` 로 나눠 각자 파일로 저장. 메인 프로세스가
   `/proc/meminfo` 를 몇 초 간격으로 감시하다 위험 수위에서 `pool.terminate()`.
   k=2, 4, (되면) 8 재시도.
3. **비트패킹 엔진** (신규 모듈, 기존 문자열 엔진은 그대로 — `CLAUDE.md` 하드룰
   4, 4×4 프로덕션 경로는 안 바꿈) + 4×4 등가성 회귀 테스트.
4. **정렬 병합 + 코어 병렬** — `numba` (`@njit(parallel=True)`, `prange`) 로
   비트패킹 표현 위에서. 문자열 dict 엔진과 벤치마크 비교.
5. **GPU 평가** — 4번이 실제로 통과한 뒤에만. `cupy` (RTX 2060, CUDA 13.1
   드라이버, `nvcc` 없음 → `cupy-cuda12x` 프리빌트 휠 사용). CPU 스레드 버전과
   같은 작업으로 벤치마크해서 **실제로 더 빠를 때만** 채택. 6GB VRAM 한계 기록.

각 단계는 그 자체로 커밋 가능한 결과물을 남기고, 실패해도 이전 단계 결과는
살아있게 설계합니다.

## 결과 (2026-08-30)

네 엔진 전부 문자열 오라클과 항 단위로 정확히 일치 확인 (`00_validate_small.py`
TEST 17~20). 4×4 실제 모델(한 청크, dt=0.01, 14000게이트)에서 실측:

| 엔진 | ~1.6K 항 | ~31.6K 항 | 비고 |
|:--|--:|--:|:--|
| 문자열 dict (기존) | 2.30s | 15.0s (기준) | |
| 비트패킹 `(x,z)` 튜플, 순수 파이썬 | — | 더 느리고 더 큼 | **부정적 결과** — 파이썬 객체는 논리적 비트폭과 무관하게 오브젝트당 ~28B 오버헤드. 문자열(65~89B)과 별 차이 없거나 더 나쁨 |
| numba JIT (`typed.Dict[uint64,f64]`) | 0.86s (2.7x) | ~13s (~1.15x, 부하 상태) / 격리 측정 시 12.7s (X_0, k=1 처음부터, ~6x) | 항 단위 루프를 그대로 JIT — 가장 낮은 위험, 실전(§2 병렬화)에 바로 채택 |
| **정렬 배열** (`union1d`+`searchsorted`, numpy) | 1.39s (numba보다 느림) | **12.0s (numba보다 빠름, 교차점)** | 벡터화 오버헤드가 작은 스케일에선 손해, 큰 스케일에서 역전 — 문서가 예견한 그대로 |
| GPU (cupy, 같은 정렬-배열 코드) | — | **100.3s (CPU numpy 대비 6.7배 느림)** | RTX 2060, 워밍업 제외. 더 큰 스케일(~120만 항, 실측된 X_6/X_10 규모) 재시도는 42분째 안 끝나 중단 — **결론 보류, 아래 참고** |

**GPU 결론 (사용자 질문에 대한 답): 지금 코드로는 아니오.** 14000개
게이트를 순차적으로 적용해야 하고(체인 하나가 다음 입력이 되므로 배칭 불가),
게이트 하나당 `union1d`/`searchsorted`/`argsort` 등 커널을 여러 번 호출합니다.
CPU→GPU 데이터 전송 없이 GPU 메모리에 계속 두더라도(이 구현이 실제로 그렇게
함), **커널 실행 자체의 고정 오버헤드**(RTX 2060 기준 호출당 수십 마이크로초)가
14000번 곱해지고, 각 커널이 처리하는 데이터가 (수만~수십만 항이라도) 이
오버헤드를 압도할 만큼 크지 않습니다. 항 수가 더 커지면(실측 120만) 이 비율이
나아질 수도 있지만 — 검증하려던 재시도가 CPU 경쟁 상태에서 42분을 넘겨
중단했습니다(다른 중요 작업에 코어를 돌려주기 위함). **미해결로 남깁니다**:
결론을 뒤집으려면 (a) 여유 있는 상태에서 벤치마크를 다시 돌리거나, (b) 게이트를
배치로 묶어 커널 호출 횟수 자체를 줄이는 재설계(예: 서로 교환하는 여러 RZZ를
한 번에)가 필요합니다. 후자는 이번 세션 범위 밖입니다.

**실전 채택**: `scripts/02b_time_sweep_parallel.py` 는 numba 엔진을 씁니다
(추가 배포 없이 검증됐고, 실측 스케일에서 이미 유의미하게 빠름). 정렬-배열
엔진은 코드베이스에 있고 (`propagation_sorted.py`) 항 수가 훨씬 커지는 국면
(7×7 이상, 또는 4×4 라도 largest 관측량이 매우 클 때)에서 다시 벤치마크할
가치가 있습니다.
